## 006: What a deploy costs, and what has already been optimised (2026-07-28)

**Decision:** Deploy cost is dominated by the **total file count in the deploy tree**, not by how many files changed. Do not re-investigate this from scratch; the measurements below are the baseline, and the optimisations listed are already in place and must not be undone.

### Measured baseline (2026-07-28, `scripts/deploy.sh --quick`)

| Quantity | Value |
|---|---|
| Files Netlify hashed | 57,563 |
| Files Netlify actually uploaded | 1,697 |
| Wall clock, whole script | ~30 min |
| Netlify CLI step alone | ~21 min |
| Local hashing throughput (measured) | ~2,900 files/sec |

The tree is ~29.9k files directly under `public/` (of which ~29.5k are HTML) plus ~27.6k Pagefind index files reached through the `public/pagefind` symlink.

**What this rules out.** Local hashing is not the bottleneck: at the measured rate the whole tree hashes in roughly 20 seconds. Re-uploading unchanged files is not happening either — only 1,697 of 57,563 files were sent. The remaining time is server-side in Netlify's CDN-diffing and atomic-deploy processing, and scales with total file count. **This has not been instrumented per phase.** Do that before attempting any further optimisation; three hypotheses were guessed and discarded on 2026-07-28 before anyone read the CLI output.

### Optimisations already in place — do not regress these

- **No asset fingerprinting** (`1763606`). CSS/JS filenames are stable and revalidated by ETag via `Cache-Control: max-age=0, must-revalidate` in `netlify.toml`. Putting the bundle hash back into asset URLs would change all ~29K HTML pages on every CSS or JS edit, which previously caused whole-site re-uploads and deploys timing out past 30 minutes.
- **`.netlifyignore` excludes `pdfs/` and `pdf-thumbnails/`** (`30acdaa`). That is ~53 GB that would otherwise be uploaded to Netlify; PDFs go to Cloudflare R2 instead (see `docs/pdf-hosting-policy.md`).
- **`public/pagefind` symlink is dereferenced for the CLI** (`e85a8fd`), or the search index does not get uploaded at all.
- **Three deploy modes exist for a reason** (`dc2c2ba`, and PUBLISHING.md "Deployment"). `--fast-note` skips the clean, the rebuild, and Pagefind. Use the cheapest mode the change allows.

### Consequence for recurring work

`--quick` costs ~30 minutes no matter how small the change, because it cleans, rebuilds all ~29.5k pages, regenerates Pagefind, and ships the full atomic tree. That is acceptable for template work and too slow for a weekly chore.

Most `gsc-indexing-triage` runs touch only `static/_redirects` and `netlify.toml`. Neither needs a Hugo rebuild — `netlify.toml` is configuration Netlify reads directly, and `_redirects` is copied verbatim into the output. A redirects-only deploy mode is the obvious next step, but note it would still pay the server-side per-deploy cost above, so measure that first to know what it actually buys.

**Rejected:**
- **Blaming the deploy time on a shared-partial edit**: guessed twice on 2026-07-28 and wrong both times. Editing `layouts/partials/head.html` did not change the minified output of pages that lack the new param, and Netlify uploaded 1,697 files, not 28,000. Read the CLI output before theorising.
- **Blaming Google Drive I/O**: `public/pagefind` resolves into `~/My Drive/`, which looks suspicious, but hashing 400 of those files took 0.14s. Not it.
